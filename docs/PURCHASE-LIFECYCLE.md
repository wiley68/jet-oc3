## Ownership and identity

A keyed purchase scope binds store 0, native session ID, customer ID, context
(product/cart/checkout), and product ID only for Product. A server-derived HMAC
of that scope and generation number is the immutable application ID. Generation 1
is stable and implicit; it needs no write merely to calculate an offer. Later
server-owned generations are durable metadata in `jet_submission`.

The active generation comes from the database, not from mutable session hints.
Product options/quantity, cart contents, checkout order ID and payment method do
not define a new generation. Jet and Jet Card share the same checkout generation.
There is no intent renewal on refresh, navigation, recalculation or cart changes.

An explicit POST `extension/mt_jet_credit/jetcredit/new_purchase` requires HTTPS,
session CSRF, the prior immutable ID, its owner and an eligible completed claim
(`complete` plus `manual_registered` or `transport_accepted`). A 32-byte random
browser token identifies retries; its keyed digest is stored. It does not assign
application identity. Ownership is checked before returning historical outcomes
or a successor. Unknown/creating/failed/held attempts cannot be renewed.

## Durable transition concurrency

The dedicated claim connection requires autocommit and InnoDB. A new-purchase
transaction locks the existing prior claim `FOR UPDATE`, rechecks ownership and
completion, and looks for its persisted successor. One predecessor has at most
one successor through `jet_successor`; `(scope,generation)` has another unique
constraint. The server derives generation N+1 and its ID. All requests for the
same predecessor, even with different click tokens, return the same child.
Replaying an earlier transition after further purchases returns its original
child, never the latest application under another identity.

The row lock serializes competing transitions; uniqueness is an independent
backstop. Nothing holds a transaction across native order creation or SMTP.
Rollback before commit leaves no child. If commit succeeds but the response is
lost, retry finds the committed child. There is no session read/modify/write
assumption and no deletion of a historical claim, counter, reference or order.
Actual server contention/uncertain network COMMIT still needs owner validation;
local shared-row doubles prove contracts and failure interleavings only.

## Offers, old requests and receipts

Offers retain the 1800-second lifetime and HMAC protection. Their signed payload
contains the immutable application ID and generation, as does the full ownership/
financial binding. A fresh submission compares its submitted ID with that signed
identity and the current generation before acquiring an executable claim. An old
offer cannot execute under a new ID. Completed claims replay before fresh-offer
validation; manual outcomes never become automatic after a settings change.

Rendered forms carry their immutable ID. A quote explicitly names it. An older
request without the field addresses generation ONE, never the active generation.
Old completed quotes return the old outcome/receipt. Old unknown quotes remain
review-required. The client checks response identity, AJAX sequence and mount
lifetime, aborts obsolete requests, and ignores delayed old quotes/transitions.

Historical receipts authorize their original intent independently of the active
pointer, against the same session/customer/store ownership and completed DB claim.
They retain 1800-second expiry. Receipt GETs do not start a purchase, send mail,
clear a cart or change an intent. Lost guest sessions cannot recover authorization
with an order ID alone. Session/key rotation can still make receipts unavailable.

## Minimal UI flow

A completed Product/Cart/Checkout quote displays its established outcome, a safe
link to its historical receipt and **“Започни нова покупка на изплащане”**. It does
not automatically redirect to the old receipt. The success page links back to the
relevant shopping context; returning there alone creates no new generation.

Only clicking the explicit button posts the transition. Retry uses the same token.
On success, old offer state is discarded, consent/EGN controls are reset, and a
fresh quote is requested with the new immutable ID. Checkout first invokes native
checkout/confirm to construct the new server-owned order data. A failed transition
or draft/quote initialization shows a controlled error, never a financing success.
A lost response may leave a durable child; retry safely resolves that same child.

## Checkout reservation and achievable guarantee

Before any non-idempotent native `addOrder()`, the dedicated repository commits a
`draft_creating` reservation, unique per intent, with owner-run nonce, owner HMAC,
scheme and server-data digest. Only the insert winner can call `addOrder()`.
Contenders see the reservation and cannot take it over, including after a crash.

After native creation, the helper reads back and compares canonical ownership,
EUR/amount, products/options and totals. It persists one `draft_bound` order ID
and a keyed read-back digest using an owner/state compare-and-set. Reuse requires
the same server request snapshot, owner, method, status 0 and unchanged read-back.
A financial snapshot or method change after binding is a controlled refusal;
restore the original method/snapshot or obtain owner review. It never silently
updates the bound order or creates another draft for the same intent. The identity
remains the same when switching Jet/Jet Card, including a refused switch.

Completed/held executable claims retain their original order for authorized
outcome replay. A genuinely new completed purchase transition obtains a separate
intent and hence a separate draft reservation. Non-Jet native behavior is unchanged.

| Failure boundary | Durable result / retry |
| --- | --- |
| Before reservation is committed | No native creation; a later successful reservation may proceed |
| After reservation, before addOrder | `draft_creating` held; no automatic second call |
| During addOrder, including partial MyISAM writes | Held reservation; native rows may remain; no automatic retry or deletion |
| After addOrder, before successful binding commit | Held reservation; possibly unbound native order; owner reconciliation |
| Binding committed, response lost | Validated reuse of the one bound order |
| After bank reservation/unknown delivery | Existing durable submission state machine remains blocked; no resend |

This guarantees one durable draft owner and at most one bound native order per
intent through this integration, and preserves one banking transport attempt per
submission claim. It does **not** claim global exactly-once physical row creation
inside arbitrary native/third-party addOrder code. A crash may leave a partial or
unbound native order. Native MyISAM writes are never assumed to roll back with
InnoDB metadata. Recovery is owner-operated; there is no automatic lease/takeover.
